# AMAR AI — Constitution of Maximum Capability and Engineering Rigor

**STATUS: CONSTITUTIONAL — PERMANENT**

## 1. Supreme principle

AMAR AI must never be simplified, weakened, downgraded, or reduced merely to make implementation, CI, testing, release, or maintenance easier.

Every correction must preserve all valid existing capabilities and, where possible, increase precision, depth, robustness, extensibility, observability, safety, and professional quality.

A smaller implementation is not considered a successful implementation when it achieves correctness by sacrificing required intelligence or capability.

## 2. Mandatory engineering rule

All development follows:

**Inspect → Correct → Deepen → Expand → Test → Audit → Document → Re-test → Final Audit → Close**

Fixes must address root causes. Patches that merely suppress failures, weaken requirements, delete tests, narrow capabilities, or bypass architectural contracts are prohibited.

## 3. Intelligence preservation rule

AMAR AI is an institutional, open-ended, continuously extensible intelligence system. It must not be treated as a simple assistant or reduced to a thin command router.

Required characteristics:
- high-precision reasoning;
- multi-step reasoning and orchestration;
- evidence-aware analysis and verification;
- persistent, provenance-aware memory;
- deep research and source comparison;
- broad code and file intelligence;
- multimodal intelligence where actual backends exist;
- self-critique and contradiction detection;
- decision intelligence with explicit uncertainty;
- strong observability and auditability;
- extensible capability and tool boundaries;
- fail-closed behavior when evidence or capability is unavailable.

## 4. Authority rule

The **AMAR AI Agent is the central authority and coordination layer** for the application and its intelligence capabilities.

UI is presentation and interaction. Engines are capability modules. Tools are governed execution surfaces. No legacy UI, external AI provider, or isolated subsystem may silently become the application's authority.

## 5. Provider independence

Gemini is permanently excluded from the architecture. No external AI provider is mandatory for core AMAR intelligence.

Provider gateways, where required by a capability, must remain optional, scoped, revocable, auditable, failure-isolated, and incapable of silently becoming the core authority.

## 6. Capability integrity

No requirement may be deleted or weakened to satisfy CI, tests, build constraints, performance shortcuts, or release deadlines.

For every declared capability, the required lifecycle is:

**Implemented → Integrated → Tested → Verified → Evidence → Final Audit**

If a capability lacks actual backend execution or test evidence, it must be explicitly marked **NOT VERIFIED / FAIL-CLOSED** rather than represented as completed.

## 7. Safety without simplification

Security and safety must be achieved through stronger architecture, explicit permissions, capability scopes, confirmation gates, provenance, audit trails, rollback, and fail-closed behavior — not by removing intelligence or functionality.

Sensitive operations require explicit authorization and confirmation. Hidden execution, hidden permissions, covert capture, security bypasses, fabricated observations, and unauthorized execution are prohibited.

## 8. Quality standard

The target is the highest technically justified level available within the project's architecture and evidence.

"Good enough", "simpler", or "passes CI" alone are not quality criteria.

A change is acceptable only when it improves or preserves the required architecture and can be supported by current evidence.

## 9. Change-control rule

Strategy, requirements, architecture, or capabilities must not be changed or removed without explicit owner approval.

Implementation defects may be corrected directly when the correction preserves the approved strategy and requirements.

## 10. Release and audit rule

No stage may be closed on historical evidence. Closure requires fresh evidence from the current revision.

The complete cycle remains:

**Inspect → Correct → Test → Confirm → Evidence → Final Audit → Close**

After each major stage, a periodic end-to-end Agent audit must verify that earlier capabilities remain intact before progression.

## 11. Constitutional interpretation

When two implementation choices are possible, prefer the choice that provides greater correctness, precision, depth, extensibility, traceability, and long-term capability without violating safety or approved architecture.

Never choose simplification solely because it is easier.

**This document is a permanent project governance rule and applies from the beginning of AMAR AI development through final release and all subsequent evolution.**
